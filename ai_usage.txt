```text
parse_program
parse_statement
parse_decl

parse_exit
parse_expr
```

It uses `peek()` and `eat()` and reads the tokens produced by your lexer—not the source text directly.

## 2. Abstract syntax tree

Added these AST classes:

```text
Node
├── ProgramNode
├── DeclNode
├── AssignNode
├── ExitNode
└── ExprNode
    ├── BinOpNode
    ├── VarNode
    ├── ConstNode
    └── BoolNode
```

Every node stores its `line` and `column`, allowing later phases to report precise errors.

`BoolNode` is technically a Practice 4 addition.

## 3. Visitor mechanism

Every AST node has:

```python
node.accept(visitor)
```

This allows the same tree to be processed independently by:

- `AstPrinter`
- `SemanticChecker`
- `CodeGenerator`

This is the main architecture required to prevent checks and LLVM instructions from being mixed together.

## 4. Expression precedence

Implemented the Practice 3 expression hierarchy:

```text
expression
└── arithmetic: + and -
    └── term: *
        └── factor: constant or variable
```

Therefore:

```text
2 + 3 * 4
```

is parsed as:

```text
2 + (3 * 4)
```

Equal-precedence operations are left-associative:

```text
10 - 3 - 2
```

becomes:

```text
(10 - 3) - 2
```

Practice 4 comparisons were added one level above arithmetic:

```text
comparison: == and !=
└── arithmetic
```

## 5. `--ast` mode

Implemented:

```bash
python3 compiler.py --ast input.txt
```

Example output:

```text
Program
  Decl x i32 const
    BinOp +
      Const 2
      BinOp *
        Const 3
        Const 4
  Exit
    Var x
```

The type shown in `Decl x i32 const` includes the Practice 4 extension.

## 6. Parser errors

The parser reports `line:column` for errors such as:

- invalid statement beginnings;
- missing `:=`;
- missing `{}` initialiser;
- invalid expression operands;
- extra tokens after a statement;
- operations where a factor is expected;
- statements after `exit`;
- missing `exit`;
- more than one comparison.

## 7. Tree-based code generation

The old Practice 2 compiler generated LLVM while examining token lists.

I replaced that with:

```text
tokens → parser → complete AST → walks over AST
```

The `CodeGenerator` now visits AST nodes:

```text
visit_program
visit_decl
visit_assign
visit_exit
visit_binop
visit_var
visit_const
visit_bool
```

This fulfills the essential Practice 3 requirement that code generation walk the tree rather than process tokens directly.

## 8. Practice 3 grammar

Added `grammar.ebnf`, including:

```text
program ::= { statement endline | endline } exit [ endline ]
statement ::= declaration | assignment
declaration ::= type [ "mut" ] ident "{" expression "}"
assignment ::= ident ":=" expression
expression ::= arithmetic [ ( "==" | "!=" ) arithmetic ]
arithmetic ::= term { ( "+" | "-" ) term }
term ::= factor { "*" factor }
factor ::= number | "true" | "false" | ident
```

It is the Practice 3 grammar expanded with Practice 4 types, booleans, and comparisons.

## Important difference

Practice 3 kept these checks in code generation:

- declared before use;
- declared only once;
- only `mut` variables may be assigned.

For Practice 4, I moved them into the separate `SemanticChecker`, as required. So the final code contains the Practice 3 functionality but uses the improved Practice 4 architecture.

# 2. Lexer

File:

```text
lexer.py
```

The lexer reads the source as raw bytes and converts characters into tokens.

For example:

```text
i64 mut y{x + 10}
```

becomes approximately:

```text
keyword     i64
keyword     mut
identifier  y
block       {
identifier  x
operator    +
number      10
block       }
```

## Keywords

The lexer recognizes:

```text
i32
i64
bool
mut
exit
true
false
```

If a word is not one of these keywords, it becomes an identifier.

For example:

```text
result
my_variable
x2
```

## Operators

It supports:

```text
+
-
*
:=
==
!=
```

`==` and `!=` use dedicated lexer states. A single `=` or `!` is rejected immediately.

Example:

```text
x = 2
```

produces:

```text
compilation error: line 1:3:
expected '==' (a single '=' is not an operator)
```

This is a **lexical error** because the invalid character sequence is detected before parsing.

# 3. Abstract syntax tree

The parser does not generate LLVM directly. It first constructs an abstract syntax tree, or AST.

The main node classes are:

```text
Node
├── ProgramNode
├── DeclNode
├── AssignNode
├── ExitNode
└── ExprNode
    ├── BinOpNode
    ├── VarNode
    ├── ConstNode
    └── BoolNode
```

## `ProgramNode`

Represents the complete program:

```python
ProgramNode(
    statements,
    exit_node,
)
```

It contains all declarations and assignments, followed by exactly one `exit`.

## `DeclNode`

Represents declarations:

```text
i64 mut y{x}
```

It stores:

```text
name       = y
type_name  = i64
mutable    = true
init       = VarNode("x")
```

## `AssignNode`

Represents assignments:

```text
y := y * z + a
```

It stores:

```text
name  = y
value = expression tree for y * z + a
```

## Expression nodes

Examples:

```text
10       → ConstNode
true     → BoolNode
x        → VarNode
x + 10   → BinOpNode
```

Every node also stores its source `line` and `column`. Therefore semantic errors can identify the exact location without needing the original tokens.

# 4. Recursive-descent parser

The `Parser` class converts tokens into the AST.

Its primary methods are:

```text
parse_program
parse_statement
parse_decl
parse_assign
parse_exit
parse_expr
parse_arith
parse_term
parse_factor
```

It uses:

```python
peek()
eat()
```

- `peek()` inspects the current token without consuming it.
- `eat()` consumes the current token and advances to the next one.

This is a hand-written recursive-descent parser, as required by Practice 3.

## Grammar levels

The relevant expression grammar is:

```text
expression ::= arithmetic [ ("==" | "!=") arithmetic ]
arithmetic ::= term { ("+" | "-") term }
term       ::= factor { "*" factor }
factor     ::= number | "true" | "false" | identifier
```

Each grammar level corresponds to a parser method.

## Precedence

Because `parse_arith()` calls `parse_term()` first, multiplication binds more strongly than addition.

This:

```text
2 + 3 * 4
```

becomes:

```text
BinOp +
  Const 2
  BinOp *
    Const 3
    Const 4
```

Therefore, the result is:

```text
2 + 12 = 14
```

not:

```text
5 * 4 = 20
```

## Left associativity

This:

```text
10 - 3 - 2
```

becomes:

```text
(10 - 3) - 2
```

The parser creates the new binary node using the expression already parsed as its left child.

## Comparisons

Comparison has lower precedence than arithmetic.

This:

```text
x * 2 != y + 5
```

becomes conceptually:

```text
(x * 2) != (y + 5)
```

Only one comparison is allowed in an expression.

It does not generate LLVM.


was parsed as:

# 6. Visitor architecture

Every AST node has an `accept()` method.

Conceptually:

```python
node.accept(visitor)
```

determines the node’s class and calls the corresponding visitor method:

```text
DeclNode   → visit_decl
AssignNode → visit_assign
BinOpNode  → visit_binop
VarNode    → visit_var
```

The same tree is processed by three independent visitors:

```text
AstPrinter
SemanticChecker
CodeGenerator
```

That means AST nodes do not need to contain parsing, checking, and LLVM logic all mixed together.

# 7. Semantic checker

The `SemanticChecker` runs after parsing and before LLVM generation:

```text
AST → SemanticChecker → checked AST
```

This is the central Practice 4 requirement.

It owns the symbol table:

```python
self.symbols = {}
```

Conceptually, entries look like:

```text
a → declaration of a, type i64, const
e → declaration of e, type bool, mut
y → declaration of y, type i64, mut
```

## Declaration checking

For:

```text
i64 y{x}
```

the checker performs these steps:

1. Ensure `y` is not already declared.
2. Check the initializer before adding `y` to the table.
3. Determine the initializer type.
4. Check whether that type can go into `i64`.
5. Add `y` to the symbol table.

Checking the initializer first correctly rejects:

```text
i32 x{x}
```

because `x` does not exist while its own initializer is checked.

## Variable resolution

When the checker sees:

```text
Var x
```

it finds `x` in the symbol table.

It then saves the resolved declaration:

```python
node.decl = declaration_of_x
```

It also saves the type:

```python
node.type = declaration_of_x.type_name
```

Therefore, code generation does not need to perform another semantic lookup.

## Assignment checking

For:

```text
y := x
```

the checker verifies:

1. `y` was declared.
2. `y` is `mut`.
3. The right-hand expression is valid.
4. The right-hand type can be assigned to `y`.

# 8. Type system

The language has:

```text
i32
i64
bool
```

## Constants

A decimal constant receives the narrowest integer type that can hold it:

```text
10          → i32
3000000000  → i64
```

A value larger than signed `i64` is rejected:

```text
99999999999999999999
```

## Widening

The only automatic conversion is:

```text
i32 → i64
```

These are valid:

```text
i32 x{10}
i64 y{x}
```

These are invalid:

```text
i64 x{3000000000}
i32 y{x}
```

The second example attempts to narrow `i64` into `i32`.

## Arithmetic

The operators are:

```text
+
-
*
```

Both operands must be integers.

Result rules:

```text
i32 + i32 → i32
i32 + i64 → i64
i64 + i32 → i64
i64 + i64 → i64
```

This is rejected:

```text
bool b{true}
i32 x{1 + b}
```

because arithmetic cannot use `bool`.

## Comparisons

Supported comparisons:

```text
==
!=
```

Valid combinations:

```text
i32  compared with i32
i32  compared with i64
i64  compared with i32
i64  compared with i64
bool compared with bool
```

The result is always:

```text
bool
```

This is invalid:

```text
bool b{true}
bool result{b == 1}
```

because `bool` cannot be compared with an integer.

# 9. Code generation

The `CodeGenerator` runs only after the complete tree passes semantic checking.

Therefore, it can trust that:

- all variables exist;
- declarations are unique;
- assignments target mutable variables;
- all expressions have valid types;
- all conversions are allowed.

## LLVM types

The language types map to LLVM like this:

```text
i32  → LLVM i32
i64  → LLVM i64
bool → LLVM i1
```

## Variables

A declaration creates an LLVM stack allocation:

```text
i32 x{10}
```

produces an `alloca i32`, followed by a `store`.

An `i64` variable uses:

```text
alloca i64
```

A boolean variable uses:

```text
alloca i1
```

## Widening with `sext`

Your command:

```bash
grep sext output.ll
```

produced:

```text
%"wide" = sext i32 %"x.value" to i64
```

This proves the compiler converted an `i32` value to `i64`.

`sext` means **sign extension**. It creates a 64-bit integer with the same signed value as the original 32-bit integer.

For:

```text
i32 x{15}
i64 y{x}
```

the compiler:

1. loads the `i32` value of `x`;
2. extends it to `i64`;
3. stores the resulting `i64` value in `y`.

## Arithmetic generation

The generator uses LLVM builder methods:

```python
builder.add(...)
builder.sub(...)
builder.mul(...)
```

It first widens operands when needed so both LLVM operands have the same width.

LLVM cannot directly perform:

```text
add i32 value, i64 value
```

Both operands must have the same LLVM type.

## Comparison generation

Comparisons use:

```python
builder.icmp_signed(...)
```

They produce LLVM `i1`, which is the representation of `bool`.

Before comparing an `i32` with an `i64`, the generator first widens the `i32`.

## Boolean output

Integer exits use:

```text
Program exit with result %lld
```

Before printing, an `i32` is widened to `i64`.

Boolean exits use:

```text
Program exit with result %s
```

LLVM `select` chooses between pointers to:

```text
true
false
```

This does not require branches.

Your command demonstrated:

```text
Program exit with result true
```

# 11. Error phases

There are now three distinct places where compilation can fail.

## Lexer errors

Examples:

```text
=
!
$
/
(
```

These characters or incomplete operators cannot form valid tokens.

## Parser errors

Examples:

```text
i32 x{}
i32 x{1 +}
x 10
exit x + 1
```

The tokens exist, but they do not follow the grammar.

## Semantic errors

Examples:

```text
i32 x{y}             # y is not declared
i32 x{1}
x := 2               # x is not mut
bool b{1}            # incorrect type
i32 x{3000000000}    # does not fit
```

The syntax is valid, but its meaning violates language rules.

Importantly, semantic errors occur before `CodeGenerator` is constructed.
