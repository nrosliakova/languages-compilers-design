# 1. Added `find_variable()`

Previously, your compiler had only `lookup()`, which either found a variable or immediately raised an error.

For call resolution, we need to ask:

> “Is there a visible variable with this name?”

Not finding one is not necessarily an error—it might be a function instead.

So I added:

```python
def find_variable(self, name):
    for frame in reversed(self.scopes):
        if name in frame:
            return frame[name]
    return None
```

### How it works

`self.scopes` contains the currently visible variable scopes.

Searching them in reverse means:

1. Look in the innermost scope.
2. Then look in surrounding scopes.
3. Return the first matching declaration.

This preserves your existing shadowing rules: a local variable can hide an outer variable or an object field.

If nothing is found, it returns `None` rather than raising an error.

### What changed in `lookup()`

`lookup()` now calls this helper:

```python
decl = self.find_variable(name)
if decl is not None:
    return decl
```

If no variable exists, it raises the **same error as before**.

So existing variable expressions keep their old behavior, while call resolution gains a non-erroring search.

## Step A: Check whether the object is callable

First, it looks up the receiver’s type:

```python
struct_node = self.structs.get(receiver.type)
```

Then it checks two conditions.

### The type must be a struct

For a built-in type, it reports something like:

```text

```

### The struct must declare a method named `call`

Otherwise:

```text
'p' is not callable: Point has no member function 'call'
```

A struct merely having a field named `call` is not enough—it must have the member function.

## Step B: Save the original object name

```python
node.callable_name = node.name
```

For:

```text

```

this saves `"triple"`.

After rewriting, the method name will be `"call"`. We still need the original name for useful diagnostics.

Without saving it, an error might mention only `call`, making it unclear which object caused the problem.

## Step C: Rewrite the node

```python
node.__class__ = MemberCallNode
node.receiver = receiver
node.name = "call"
```

Conceptually:

```text
Before:
CallNode
    name: triple
    args: [14]

After:
MemberCallNode
    receiver: triple
    name: call
    args: [14]
```

The argument list stays unchanged.

### Why change the node in place?

Other AST nodes already hold references to this expression.

For example:

```text
PrintNode
    └── CallNode triple
```

If we only created a new node in a local variable, the `PrintNode` would still point to the old one.

Changing the existing object preserves those parent references.

This is an unusual Python technique, but it works here because these AST dataclasses use ordinary instance dictionaries rather than incompatible slot layouts.

# 3. Parser: distinguish lambdas from ordinary functions

## Added `is_lambda()`

This helper checks whether the current tokens begin with:

```text
fn name := [
```

That distinguishes:

```text
fn square := (i32 x) -> i32
```

from:

```text
fn square := [](i32 x) -> i32
```

The first is an ordinary function. The second is a lambda with no captures.

## Changed `parse_program()`

Previously, a top-level `fn` was always handled as an ordinary function declaration.

Now:

- Ordinary functions still follow the existing placement rules.
- Lambdas are handled as **statements**.

Therefore, this is valid:

```text
i32 k{10}

fn add_k := [k](i32 y) -> i32
{
    i32 r{k + y}
    exit r
}
```

The lambda can appear after a variable declaration because it belongs among the executable statements.

## Changed `parse_statement()`

When a statement starts with `fn`:

- If it has lambda syntax, parse it.
- Otherwise, keep the existing error for an ordinary nested function.

This permits lambdas inside:

- Functions.
- Member functions.
- `if` and `else` blocks.
- Loops.
- Other lambdas.

It does **not** permit ordinary nested functions without a capture list.

## Extended `parse_fn()`

Its signature is now:

```python
def parse_fn(self, allow_lambda=False):
```

The parser reuses the existing code for:

- Parameters.
- Return type.
- Opening brace.
- Body.
- Required final `exit`.

The added part reads an optional capture list when lambda parsing is allowed:

```text

[k]
[k, factor]
```

It returns:

- A `FnNode` for an ordinary function.
- A `LambdaNode` for a lambda.

A lambda’s parameter list and body have the same structure as an ordinary function’s. Reusing the parser avoids maintaining two nearly identical implementations.

# 5. Added `visit_lambda()`: the main semantic rewrite

This method performs most of Task 2.

## Step A: check the new variable’s name

A lambda creates a variable in the current scope.

Therefore, this is rejected:

```text
i32 f{1}
fn f := []() -> i32
{
    exit 1
}
```

It would declare `f` twice in the same scope.

Shadowing an outer scope remains allowed.

## Step B: resolve each capture

For every capture, the checker:

1. Checks whether its name already appeared in the list.
2. Looks up the variable in the currently visible scopes.
3. Reads its type.
4. Creates a corresponding const field.
5. Creates a variable expression representing the value to copy.

For:

```text
[k]
```

where `k` is `i32`, the generated field is conceptually:

```text
Field k i32 const
```

The initializer expression points to the **original declaration of `k`**.

That connection is later used to load the original value when the lambda declaration executes.

### Duplicate capture

```text
[k, k]
```

is rejected at the second `k`.

### Unknown capture

```text
[missing]
```

is rejected if no variable named `missing` is visible at that declaration.

Functions cannot be captured merely by naming them: the capture list resolves variables.

## Step C: reject parameter/capture collisions

This is rejected:

```text
fn f := [x](i32 x) -> i32
```

The body would otherwise have both a parameter and capture named `x`.

Local declarations can still shadow captures according to the existing scope rules.

## Step D: generate the struct and method

For `add_k`, the checker creates approximately:

```text
Struct lambda.add_k
    Field k i32 const
    MemberFn call -> i32
        Param y i32
        Body of add_k
```

The generated method reuses the lambda’s:

- Parameters.
- Return type.
- Body.

The struct is registered with the existing struct/type machinery, and its method signature is checked through the existing method machinery.

## Step E: check the body in an isolated scope

The checker enters the generated `call` method.

Its visible variable scopes contain only:

- Capture fields.
- Parameters.
- Locals declared in the body.

Global functions remain callable.

The enclosing function’s locals and enclosing struct’s fields are **not automatically available**. They must be captured.

## Step F: create the closure variable

After the body has been checked, the checker creates the equivalent of:

```text
lambda.add_k add_k{k}
```

This synthesized declaration is stored in:

```python
node.declaration
```

Only then is `add_k` added to the surrounding scope.

That timing is important: the lambda’s own variable is not visible while checking its body.

# 7. Kept “mutable” separate from “mutating”

These are different concepts:

- **Mutable:** the object is permitted to change.
- **Mutating method:** the method actually changes the object, directly or through another call.

For example:

```text
fn value := [mut n]() -> i32
{
    exit n
}
```

The closure variable is mutable because it has a mutable capture.

But its method only reads `n`, so the method is **not mutating**.

A const copy of that closure can therefore still be called:

```text
fn wrapper := [value]() -> i32
{
    exit value()
}
```

One of the new tests specifically checks this distinction.

# 9. How the bonus example works

The required output is:

```text

2
34
3
Program exit with result 0
```

Step by step:

1. Original `n` starts at `0`.
2. `next` captures its own mutable copy, also initially `0`.
3. Two calls to `next()` change that copy to `1`, then `2`.
4. `twice` captures a mutable copy of `next` **at its current state of `2`**.
5. Calling `twice()` advances its copied counter to `3`, then `4`, returning `34`.
6. The original `next` still has counter `2`; its next call returns `3`.
7. Original `n` is still `0`.

There are three separate pieces of state:

```text
Original n                  0
Counter inside next         3
Counter inside twice.next   4
```
